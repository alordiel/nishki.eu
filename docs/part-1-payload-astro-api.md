# Part 1 — A static site with a real CMS: Payload + Astro + a small API

*Series: building and running a CMS-backed static website on your own server.*
*Part 1: architecture · [Part 2: VPS + Cloudflare deployment](part-2-vps-cloudflare-deploy.md) · [Part 3: email, backups and admin protection](part-3-email-backups-access.md)*

---

## The goal

A small business website — a portfolio, a few content pages, a gallery, a contact form — with three requirements that usually pull in different directions:

1. **Editors must be able to change everything** (texts, photos, page layout, translations) without a developer.
2. **The public site must be fast, cheap and hard to break.**
3. **It should run on one modest server** that the owner already pays for.

The classic answer to (1) is WordPress, which makes (2) and (3) harder: every visitor hits PHP and a database, plugins need constant updates, and the admin is part of the public site.

The answer used here splits the system in two:

- **Payload CMS** for editing: a modern headless CMS written in TypeScript. It runs inside Next.js.
- **Astro** for the public site. At publish time Astro fetches all content from Payload and generates **plain static HTML**.

Visitors only ever receive static files. The CMS sits behind it and is used by editors, by the build process and by one public endpoint: the contact form.

## The big picture

```
                          ┌──────────────────────────────┐
   Editors ──────────────▶│  admin.example.com           │
   (browser)              │  Payload admin UI            │
                          │                              │      one Node.js process
                          │  api.example.com             │      (Payload inside Next.js)
   Visitors' browsers ───▶│  POST /contact   GET /health │      + SQLite database
   (contact form only)    │                              │      + media folder
                          │  REST API (read with key) ◀──┼──┐
                          └──────────────────────────────┘  │
                                                            │ build: fetch content
                          ┌──────────────────────────────┐  │ + download images
   Visitors ─────────────▶│  example.com                 │  │
                          │  static HTML/CSS/JS/images   │◀─┘ "Publish site"
                          │  generated by Astro          │    writes a new release
                          └──────────────────────────────┘
```

There are three host names, but only **two moving parts**:

| Host | What it is | Who uses it |
|---|---|---|
| `example.com` | Static files built by Astro | Everyone |
| `admin.example.com` | Payload's admin UI (and the API calls the admin makes) | Editors |
| `api.example.com` | Content API for the build, the contact form endpoint, the health check | The build process, visitors' browsers (the form only), the uptime monitor |

`admin.` and `api.` are **the same Node.js process**. A small piece of routing code looks at the requested host name and decides what each host may show. The admin UI is only served on `admin.`, and requests for `/admin` on `api.` are redirected there. One process means one thing to deploy, monitor and back up.

Why have two names at all? Separation of concerns at the network edge:

- You can put extra protection in front of `admin.` (IP allow-lists, Cloudflare Access — see Part 3) without breaking the contact form.
- `api.` can have strict CORS rules and rate limits tuned for anonymous traffic.
- If you ever split the processes, the URLs don't change.

## Repository layout

A pnpm monorepo keeps both apps and their shared types together:

```
apps/
  cms/        Payload CMS (Next.js app)      → admin.example.com, api.example.com
  web/        Astro static site              → example.com
packages/
  types/      TypeScript types generated from the Payload config
deploy/       build/deploy scripts, backup/restore, Nginx, PM2, cron examples
.github/      CI: build and deploy the CMS
```

`packages/types` is a small but valuable detail. Payload can generate TypeScript types from its collection definitions. The Astro app imports those types, so if an editor-facing field is renamed in the CMS, the site's build fails to type-check instead of silently rendering nothing.

## Modelling content: pages made of blocks

The most important design decision is **how content is shaped**, because it decides how much freedom editors get and how much the frontend has to handle.

### Collections and globals

- **Pages** — every page (home, about, gallery, prices, contact, privacy) is a list of **blocks**.
- **Projects** — portfolio entries with a cover, metadata (names, venue, season) and their own flexible gallery.
- **Media** — uploaded images with alt text.
- **Submissions** — contact form entries.
- **Users** — with roles (see below).
- **Globals** (single documents): site settings (logo, social links, footer), navigation, and a "build status" record used by the publish button.

### Blocks: one CMS block = one frontend component

A *block* is a reusable section type: hero, rich text, image banner, testimonial, FAQ, tiles, project grid, collage, contact form, call to action…

```
Payload block definition            Astro component
(apps/cms/src/blocks)               (apps/web/src/components/blocks)
────────────────────────            ───────────────────────────────
hero         { image, title, … }  →  Hero.astro
faq          { items[] }          →  Faq.astro
collage      { images[] }         →  Collage.astro
contactForm  { intro, … }         →  ContactForm.astro
…                                    …
```

A single `BlockRenderer` component maps each block type to its component. Editors build pages by adding, removing and reordering blocks. Developers add a new section type by writing two small files (the field definition and the component) and one line in the renderer.

This gives editors real layout freedom ("three rows of photos, a paragraph, two more rows" on one project, no text at all on another) without the free-for-all of a page builder that can break the design.

### Localisation

All text fields are localised (here: two languages, the default at `/`, the second at `/en/`). Layout and photos are shared between languages, so editors don't rebuild every page twice — they switch the language and translate the text.

### Drafts

Pages and projects have draft/published status. The build only fetches **published** documents, so editors can prepare changes without them going live on the next publish.

## The build: how the CMS becomes a static site

When an editor clicks **Publish site**, Astro runs a full build:

1. **Fetch content.** Astro calls Payload's REST API (`/api/pages`, `/api/projects`, globals) for each language.
2. **Generate routes.** Every page slug becomes `/<slug>/` (and `/en/<slug>/`), every project becomes `/gallery/<slug>/`. The page with slug `home` becomes `/`.
3. **Download and optimise images.** Every image referenced by the content is downloaded from the CMS and re-encoded by Astro into modern formats in several sizes (`srcset`). The result goes into the build output.
4. **Write files.** HTML, CSS, JS, images, `sitemap-index.xml`, `robots.txt`, a `404.html`.

The output is a folder you could put on any web server, S3 bucket or CDN. **No request from a visitor ever reaches the CMS** — not even for images. That is the property that makes the public site fast and resilient: if the CMS process crashes, the site keeps working, and only editing and the contact form are affected.

### A dedicated "build" user

The build reads content with an **API key belonging to a dedicated user with a read-only `build` role**, never with a person's account:

| Role | Can do |
|---|---|
| `admin` | Everything, including users and deleting submissions |
| `editor` | Edit content, publish, review submissions |
| `build` | Read published content. Nothing else |

If the key leaks, it can read content that is about to be public anyway — it cannot edit anything or read submissions.

Other access decisions:

- **Media files are publicly readable.** They end up on the public site anyway. Pages, projects, settings and submissions require a key or login.
- **GraphQL is disabled.** It's unused, so turning it off shrinks the attack surface.
- **Failed logins lock the account** for 15 minutes after 5 attempts.

### Images: let the build do the heavy lifting

Photographers upload camera-size files. Payload keeps a downscaled master (e.g. 2560 px wide) plus a thumbnail for the admin, and the build generates all the responsive sizes the site needs. This keeps uploads fast, keeps builds reasonably quick, and means the static site is self-contained.

## The Publish button

Publishing is a button in the admin header, not a deploy step a developer has to run.

```
Editor clicks "Publish site"
        │
        ▼
POST /api/publish  ──▶  already building?  ── yes ──▶ mark "queued" (exactly one follow-up)
        │                      │
        │                      no
        ▼                      ▼
   status: running      run the build (one of two modes)
        │
        ▼
   status: live since … / failed + last lines of the log
```

Behaviour worth copying:

- **One build at a time.** Clicks during a build queue *exactly one* follow-up build, so five quick clicks don't start five builds, and the last change is never lost.
- **Visible status.** "Live since 14:02" or "Failed" with the tail of the build log, shown next to the button and on a status page. Editors don't need SSH access to find out what happened.
- **Two modes, one switch:**
  - `local` — the CMS runs a deploy script on the same server: build, copy the output into a new release folder, atomically switch the live symlink (details in Part 2).
  - `hook` — the CMS calls a webhook (e.g. a CI workflow that builds and uploads to a CDN), and CI reports the result back to a callback endpoint.

The lock and queue live in the process's memory, which is one reason the CMS deliberately runs as **a single process** (Part 2).

**Content changes** (editor edits a page → Publish) and **code changes** (developer pushes to Git → CI deploy) are separate pipelines. Editors never wait for CI, and developers never need to touch content to ship code.

## api.example.com: the contact form endpoint

The static site has one interactive feature: the contact form. It posts directly from the visitor's browser to `https://api.example.com/contact`, which is a custom route inside the Payload app.

The handler runs these checks **in this order**. Each one is cheaper than the next, so junk is rejected before any expensive work:

```
1. CORS / Origin      only https://example.com (and www) may post
2. Rate limit         5 submissions / 10 minutes / IP
3. Honeypot           a hidden field humans never fill in
4. Turnstile          Cloudflare's invisible CAPTCHA, verified server-side
5. Validation         required fields, lengths, allowed values
6. SAVE               the submission is stored in the CMS  ← always before email
7. Email the owner    reply-to = the person who filled in the form
8. Auto-reply         optional, in the visitor's language
```

Two decisions make this robust:

- **Save first, email second.** If the email provider is down or misconfigured, the submission is still in the admin, and the email error is recorded on it. You never lose an enquiry to an SMTP problem.
- **Reply-to is the visitor.** The owner hits *Reply* in their normal mail client and is talking to the customer.

The response contract is deliberately small: `200 {ok:true}`, or an error code (`validation`, `captcha`, `rate_limited`, `origin`, `server`) that the frontend maps to a translated message.

### GDPR basics built in

- Privacy notice linked under the form.
- Submissions are **automatically deleted** after N months (a nightly script — Part 3).
- Admins can delete individual submissions on request; editors can only change their status (new / read / archived).

### The health endpoint

`GET https://api.example.com/health` returns `{"ok":true}` only if the app is up **and** the database answers a query. It's used by the deploy pipeline (to decide whether to roll back) and by the uptime monitor. A health check that only proves "the process is listening" misses half the failures.

## Security headers and a script-free-ish frontend

Because the site is static, its security policy can be strict:

- A **Content Security Policy** that allows scripts only from the site itself and from Cloudflare's Turnstile, and network requests only to the site and `api.example.com`.
- All scripts are emitted as external files (no inline scripts), so the CSP doesn't need `'unsafe-inline'` for scripts.
- Fonts are self-hosted — no third-party font requests, which is also a GDPR win.

These headers are sent by the web server, not by Astro. Part 2 covers how.

## Database: SQLite (and when not to)

The CMS uses **SQLite**: a single file on disk.

- Zero administration, no separate database server, trivially backed up (Part 3).
- More than fast enough for one site with a handful of editors and modest traffic, since visitors never touch it.
- The limitation is that **one process** writes to it. That matches the single-process design anyway. If you ever need several app servers, swap the Payload adapter for Postgres.

### Migrations: the trap on the first production start

In development, Payload "pushes" the schema: it creates and alters tables automatically to match your config. **In production it deliberately doesn't** — schema changes must be explicit.

So a fresh production database starts **empty**, and the first request fails with "no such table". The fix is a normal migration workflow:

1. After changing collections or fields, generate a migration (`payload migrate:create <name>`) and commit it.
2. Configure the database adapter to **run pending migrations on startup** in production (`prodMigrations`).

Now every deploy that includes a schema change applies it automatically when the new version starts, and a brand-new server creates all tables on first boot.

## Checklist for this architecture

- [ ] Content modelled as **collections + blocks**, one block ↔ one component
- [ ] Types generated from the CMS and used by the frontend
- [ ] A dedicated **read-only build user** with its own API key
- [ ] Build downloads and optimises images, so the output is **self-contained**
- [ ] **Publish button** with a single lock, one queued follow-up and visible status
- [ ] Contact endpoint ordered **cheap checks → save → email**
- [ ] `/health` that checks the **database**, not just the process
- [ ] Migrations committed and applied **on startup** in production
